## 2. 重启会丢什么

**唯一会丢的是 `force_route=direct`。**

- 它只存在于 v1.1.0 进程内存（`retry_proxy.py` 的 `SETTINGS` dict），`/__control` 写入后不落盘。
- runtime 目录 `%USERPROFILE%\.config\opencode\oc-error-monitor-v1.1.0` 里只有 `deployed.json` 和 `retry_proxy.log.jsonl`，没有 settings 文件。
- **重启后自动回 `force_route=null`（auto）**，流量重新走 CF 通道，429 回归，且不会有任何提示。
- 依据：同模型 `deepseek-v4.1-flash-free` direct 197/197 = 100%，proxy 53/76 = 69.7%，差额全是 429。

不会丢的：

- 日志 `retry_proxy.log.jsonl` 在磁盘上，重启后还在。
- 代码、配置、报告、git 历史全在仓库。

## 3. 重启后恢复步骤

1. 等计划任务拉起；没起来就手动：

   ```
   oc-error-monitor\launcher\launch.bat 1.1.0
   oc-error-monitor\launcher\launch.bat 1.2.0-dev
   ```

   查状态：`oc-error-monitor\launcher\launch.bat status`

2. 确认端口活着：

   ```
   curl -sS http://127.0.0.1:8788/__stats
   ```

3. **把 direct 贴回去**（仍想要 direct 效果时）：

   ```
   curl -sS -X POST http://127.0.0.1:8788/__control -H "Content-Type: application/json" -d "{\"force_route\":\"direct\"}"
   ```

   验证回显里出现 `"force_route": "direct"`。

4. 确认 mihomo 起来了：节点名带 emoji，别在 GBK 控制台里直接打，写 UTF-8 文件传参。

## 5. 待办：路由从「二值枚举」改成「池 + 策略」

用户明确要求：**选项多留，不要写死**。后续会加很多 cfnew（GitHub）部署的 CF Worker 节点，节点不稳定。

### 5.1 模型

```
池成员 = mihomo 组内所有节点（自动发现） + 伪成员 DIRECT
每成员记账 {ok, fail_by_class, last_fail_ts, ewma_ms, cooldown_until}，按 mihomo 节点名做 key
选择器 = 字符串注册的 strategy，不是枚举
```

### 5.2 schema 草案

```json
{
  "schema": 1,
  "pool":   { "mihomo_group": "🎯 OpenCode专用", "extra_members": ["DIRECT"], "refresh_s": 30 },
  "select": { "strategy": "least_fail", "pin": null,
              "window_s": 600, "threshold": 3, "cooldown_s": 120, "decay_half_life_s": 3600 },
  "rotate_on": ["AUTH_IP_REPUTATION", "RATE_LIMIT", "CONNECT", "TIMEOUT"],
  "fallback":  ["proxy", "direct"],
  "probe":     { "enabled": true, "interval_s": 60,
                 "target": "http://cp.cloudflare.com/generate_204", "timeout_s": 5 },
  "persist":   { "path": "route_state.json", "fsync_s": 30 }
}
```

### 5.3 三条不写死的措施

1. `strategy` 用字符串注册，后续加 `ewma_ok` / `lowest_latency` / `weighted_random` / `round_robin` 不改 schema。
2. `rotate_on` 是可扩展列表；未知字段原样保留（读改写不丢键）；带 schema 版本号。
3. 池从 mihomo 组自动发现，Clash 里加节点代理零改动。

### 5.4 cfnew 带来的两个硬约束

1. **不能假设所有节点同一 uuid。** 现在 216 个共用同一 uuid、一个 ws path、一个 servername，是同一批部署。cfnew 每次部署到 Worker/Pages 都是新的 workers.dev 或自定义域 + 新 UUID + 新 path，可能 vless 也可能 trojan。健康记录必须按节点名，新节点从中性起步，不继承老节点历史。
2. **两层健康分开记。** L1 连通性探针测节点死活；L2 真实请求结果测网关拒不拒。混在一起会把 403/429 误判成节点已死。

### 5.5 分层实施

| 层 | 内容 | 触发条件 |
|---|---|---|
| L0 | 配置持久化、池自动发现、DIRECT 入池 | 现在就有用 |
| L1 | 连通性探针、按节点冷却 | 节点多起来之后 |
| L2 | 真实流量按节点记账、按失败类轮换 | 想压 429 时 |
| L3 | 加权 / 延迟择优、跨节点并发探测 | 节点多到手动挑不过来 |

用户尚未选定从哪层开始。

## 8. 已知风险

- `force_route=direct` 无持久化，这是本轮唯一未修的即时坑；修它就是 L0 的第一件事。
- `deepseek-v4-flash-free` 模型名在 opencode 侧不存在，会产生 HTTP400，别把这类错误混进网络统计。
- mihomo 节点名含 emoji，任何脚本读写都走 UTF-8 文件，不靠控制台参数。
