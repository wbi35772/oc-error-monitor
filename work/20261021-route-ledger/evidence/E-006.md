# E-006 · 死节点成族：96/216 每轮全死且扎堆

**severity**: high

## 观察（承接上一版报告 E-009 / E-010）

216 个可测成员里 **96 个（44%）在每一轮测速中 0 存活**，而且**不是散落的**：

| 族 | 数量 | 状态 |
|---|---|---|
| `优选域名` | 66 | 每轮 0 存活；ECH 主机名握手失败（TLS 只在用节点自己的 SNI 时失败） |
| `IPv6优选` | 30 | 每轮 0 存活；server 是裸 v6 字面量，mihomo `ipv6:false` 且本机无 v6 出口 |
| 其余四族（多线/电信/移动/联通） | 120 | 两轮之间仅 6.0% 翻转 |

## 为什么这决定了设计

逐成员冷却 = 逐个撞完整族。实测一个请求连撞：

```
IPv6优选-01 → IPv6优选-02 → IPv6优选-03 → IPv6优选-04
```

四次尝试全部 `ERR:URLError`（SSL EOF），全部落在同一个死族里。四次重试本该救回请求，实际是把一个必死的族从头走到尾。

对 cfnew 的影响同样直接：每批新部署的 Worker 若是同族同死，逐个冷却要付出 N 次失败才轮过去。

## 修复

`select.family_threshold`（默认 3）+ `select.family_cooldown_s`（默认 900）：同一族里连续 N 个成员在 `window_s` 内失败，整族跳过 N 秒。

两条边界：

1. **孤立节点不连坐**。族里只有它自己时（没有兄弟可参照），不写族账、不族冷却——否则一批新的 cfnew Worker 会因为彼此同名而互相连坐。
2. 族冷却由 `rotate_on` 里的失败类触发，与成员冷却同一套判定，不另起规则。

## 回归测试

`test_route_policy.py::FamilyCooldown`（11 例）：一个成员不连坐全族、三个成员判死全族、阈值可配、族冷却会过期、孤立节点不连坐、窗口外的失败不计入、clear 同时清族账、切换记录带族名、`/__route` 报告族状态。

## 复现

```bash
python test_route_policy.py FamilyCooldown -v
```
