## 这一版想解决什么

用户的要求很清楚：**不要写死**。理由也清楚：节点来自一个会自动更新的订阅池，还在陆续加 cfnew（GitHub 仓库 → Cloudflare Worker 部署）。每个新部署的域名、uuid、path 都不同。所以任何把节点名、uuid、分组名写进代码的做法都会立刻过期。

## 设计上的几次摇摆

### 「池」还是「表」

一开始想直接在 `route` 配置里写一个节点名单。写到一半发现不行：名单得手工维护，而池子是 mihomo 里客观存在的东西，每次从控制器读一次就够。于是改成「池从 mihomo 组实时发现，DIRECT 作为伪成员入池」。

顺带解决了「直连还是走代理」这个二值开关的尴尬：DIRECT 本来就是池里的一员，不该是一个模式。

### 哪些失败该换节点

这是最花时间的地方。三层词汇要分清：

- 日志要说的是**发生了什么**（`IP_REP`、`RATE`、`ERR:URLError`）
- 策略要说的是**什么允许动出口 IP**（`NET_*` 四个）
- 控制器里已有一套经回测确定的集合：`SWITCH_CLASSES`，`NO_SWITCH_REASONS` 是它的反面

我第一版自创了一套（`AUTH_IP_REPUTATION,RATE_LIMIT,CONNECT,TIMEOUT`），既有 `RATE_LIMIT`（限流要退避，轮换会掩盖原因），也有自造的 `CONNECT`/`TIMEOUT`（控制器里的名字是 `NET_CONNECT`/`NET_TIMEOUT`）。而且 `ERR:URLError` 两边都不属于——**最该触发轮换的那一类，恰恰从不触发**。真机请求连撞四个死节点而无人被冷却，就是这么来的。

最后加了一层翻译，把日志词汇映射到策略词汇，认不出来的原样返回：只记账，永不轮换。错一次轮换的代价是动所有人的出口 IP。

### 阈值该是 1 还是 3

控制器里 `PERSISTENT_MIN_FAILURES = 1`，而回测说「等 3 次爆发是反效果：到阈值的 6 个全是误报，会话早已恢复」。所以用 1。

一开始 schema 草稿里写的是 3，是照着「至少攒几次再换」的直觉写的；读完回测理由后改成 1，并且用测试把它钉在 `controller.SWITCH_CLASSES` 旁边，防止以后又漂移。

### 族级冷却是被真机请求逼出来的

第一次真机请求就撞了 `IPv6优选` 的四个成员，四个全死。查上一版的报告才知道：44% 的成员是死的，而且**扎堆在两个族里**。

逐成员冷却等于逐个撞完整族。族级冷却的做法很土：同一族里连续 3 个成员在 10 分钟内失败，整族跳过 15 分钟。

但有个陷阱：**孤立节点不能连坐**。一批新的 cfnew Worker 如果名字里没有 `-NN` 后缀，每个都是自己的一族，按族计数会互相连坐——刚部署的节点还没被试过就因为「同族」被跳过。所以族里只有自己时，不写族账。

## 三个 bug 的共同点

三个 bug 有一个共同形状：**看起来在做事，实际上没做**。

- 策略选了成员但从不记账 → 看起来在轮换，其实在重挑
- 账本记了但词汇对不上 → 看起来在记账，其实在空转
- 零数据时 DIRECT 赢 → 看起来在用池，其实在绕开它

共同的教训是：**没有可观测的量，就没有行为**。`switches` 恒为 0 那个现象，是「账本没写回」这件事唯一的信号。日志里加上 `member` 与 `via` 两个字段之后，路由的每一次决定才看得见。

## 差点又写死一次

`route` 块第一版整块落盘。改了一个默认值之后，运行中的实例不认——因为文件里的整块 route 覆盖了默认值。**默认值被冻死**。改法是只落盘差量：默认值的改动能传到已经有文件的实例，用户显式改过的仍然保留。

同一批里还犯了个更蠢的错：用 PowerShell 改 UTF-8 的 HTML 文件，`Get-Content` 按 ANSI 读，中文全成乱码，换行从 CRLF 变 LF，而 `Replace` 因为换行风格不匹配根本没生效——三个问题叠在一起，工具一声不吭。恢复办法是从运行目录那份好的复制回来，再用 python 字节级转回 CRLF。

那条教训后来写进了 E-011：**改完必须校验中文在不在、换行对不对、字节数变没变。**

## 生产上出过一次事故

用户手动停了生产（`stopped.by-user`，`by: "switch"`）。恢复时发现 v1.1.0 重启后回到 `attempts=4` / `route=null`，得手工补 `force_route=direct` 和 `attempts=10`——这正是 L0 要解决的，也说明 L0 最终要回移生产。

还发现旧生产进程的时钟落后 3 小时：停止标记里写 `08:43:52`，文件 mtime 是 `11:43:52`，机器时区 Eastern Standard Time (-05:00)。新进程的时间戳与机器时钟一致。日志时间对不上会让「哪段时间发生了什么」彻底错乱，值得单独记一笔。

## 下一步

最该先做的不是再加功能，是一个对照实验：**429 到底是不是按出口 IP 记的**。

现在的推断是「是」——因为 direct 路径 0 次 429、proxy 路径 43 次 429，且 proxy 的出口全是共享的 CF 地址。但这是推断，不是实验。同节点连打 vs 换节点连打，同模型同请求各 N 次，就能定论。

这个答案决定后面还有没有意义继续做路由：如果换节点根本改变不了 429，那 429 就绑在账号/网关侧，路由做得再好也没用；如果能改变，那策略就该去挑低限流的出口。
